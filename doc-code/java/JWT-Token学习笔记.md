# JWT Token 学习笔记：从 Cookie/Session 到 JWT

## 1. 传统的认证方式：Cookie 与 Session

HTTP 协议本身是**无状态**的，这意味着服务器默认不知道两次请求是否来自同一个用户。为了解决这个问题，传统的 Web 开发通常采用 **Cookie + Session** 的模式。

### 工作流程

1. **用户登录**：用户输入账号密码发送请求。
2. **创建会话**：服务器验证通过后，在服务器端（内存、Redis 或数据库）创建一个 **Session** 对象，记录用户 ID、登录状态等信息。
3. **分发凭证**：服务器生成一个唯一的 **Session ID**，将其通过 **Cookie** 返回给浏览器。
4. **自动携带**：浏览器后续向同域名发送请求时，会自动在请求头中带上这个 Cookie。
5. **服务端验证**：服务器拿到 Session ID，去存储中查找对应的 Session，从而确认用户身份。

### 优缺点分析

- **优点**：
  - 服务端可控性强，可以随时让 Session 失效（如踢人下线、封号、修改密码后立即失效）。
- **缺点**：
  - **服务端压力**：服务器需要存储大量 Session 数据。
  - **扩展性差**：在集群/分布式部署时，需要解决 **Session 共享** 问题（如使用 Redis 集中存储）。
  - **跨域/多端支持弱**：在前后端分离、App、小程序或跨域场景下，Cookie 的自动携带机制往往受限，配置较为繁琐。

---

## 2. JWT 的诞生背景

**JWT (JSON Web Token)** 是一种开放标准，它出现的初衷是为了实现**无状态认证**。

### 核心理念

**把用户信息直接放进令牌（Token）里，服务器不再保存会话状态。**

### 为什么需要 JWT？

随着前后端分离架构、移动端 App 和微服务的流行，传统 Session 模式显得笨重。JWT 带来了以下优势：

- **无状态**：服务器不需要存储 Session，减轻了存储压力。
- **易于扩展**：多台服务器只需使用同一个密钥即可验证 Token，天然支持负载均衡和集群。
- **跨平台/跨域**：Token 可以放在 HTTP 请求头中，完美支持 App、小程序、前后端分离项目。

### JWT 的潜在风险

- **注销困难**：一旦签发，在过期前很难主动作废（除非引入额外的黑名单机制）。
- **体积较大**：相比简单的 Session ID，JWT 包含更多信息，占用更多带宽。
- **安全性误区**：Payload 只是编码而非加密，**严禁存放密码、身份证等敏感信息**。

---

## 3. JWT 的结构详解

一个典型的 JWT 字符串由三部分组成，中间用 `.` 分隔：

`Header.Payload.Signature`

### 3.1 Header（头部）

声明令牌的类型和使用的签名算法。

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

这部分经过 Base64Url 编码形成 JWT 的第一部分。

### 3.2 Payload（载荷）

存放实际传输的数据（Claims），通常包含用户信息和过期时间。

```json
{
  "sub": "1001",
  "role": "user",
  "exp": 1730000000,
  "iat": 1729990000
}
```

字段含义：

- `sub`：用户 ID
- `role`：角色
- `exp`：过期时间
- `iat`：签发时间

注意：这部分经过 Base64Url 编码形成 JWT 的第二部分。**任何人都可以解码看到内容**，所以不要放秘密。

### 3.3 Signature（签名）

这是 JWT 的核心安全机制，用于防止数据被篡改。以 HS256 算法为例，签名生成逻辑如下：

```text
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secretKey  // 服务器端的密钥
)
```

## 4. 核心误区纠正（重要）

在学习过程中，很容易对 JWT 的验证机制产生误解。以下是常见的理解偏差与正确概念的对比：

| 常见误区                         | 正确理解                                                     |
| :------------------------------- | :----------------------------------------------------------- |
| JWT 只有"信息"和"加密结果"两部分 | JWT 由 **Header、Payload、Signature** 三部分组成             |
| 加密算法/规则存储在客户端        | 算法是公开的，但**签名密钥 (Secret) 必须严格保存在服务器端** |
| 客户端重新计算加密来验证一致性   | **验证完全由服务器完成**，客户端只负责存储和携带 Token       |
| JWT 靠"加密"来保护信息           | JWT 默认靠**"签名"防篡改**，Payload 内容通常是**可见的**     |

### 正确的交互流程

1. **登录**：用户登录成功。
2. **签发**：服务器生成 Header 和 Payload，使用**服务器私有的密钥**生成 Signature。
3. **返回**：服务器将拼接好的 JWT 返回给客户端。
4. **存储**：客户端将其存储在 localStorage、内存或 Cookie 中。
5. **携带**：后续请求在 Header 中携带 Token：

   ```http
   Authorization: Bearer <token>
   ```

6. **验证**：服务器收到请求，使用同样的算法和**服务器端的密钥**重新计算签名。
7. **比对**：如果计算出的签名与 Token 中的签名一致，且未过期，则通过验证。

---

## 5. 总结

> **一句话记忆 JWT：**
> JWT 不是让客户端证明自己是谁，而是让服务器确认**"这张通行证是不是我签发的、有没有被改过"**。

### 学习路线建议

如果你正在学习 Java 后端开发，接下来的进阶步骤可以是：

1. 在 Spring Boot 中集成 JWT 库（如 `jjwt` 或 `java-jwt`）。
2. 编写拦截器或过滤器，实现 Token 的解析与验证。
3. 设计 **Access Token + Refresh Token** 双令牌机制，解决 JWT 无法主动注销的问题。

# JWT 实战三问：用户删除、敏感信息存储与验签性能

## 问题一：JWT 还生效，但数据库里用户已被删除，操作会怎样？

**会出问题，但不应该等到业务操作时才报错。**

### 原因

JWT 验签只能证明：

- Token 是服务器签发的；
- 没有被篡改；
- 没有过期。

它**不能证明数据库里的用户仍然存在**。

所以如果用户已经被删除，但 Token 仍在有效期内，请求仍可能通过 JWT 验签。之后如果业务代码用 `userId` 查询用户、下单、修改地址，就可能出现：

- 查询用户返回 `null`；
- 插入订单时外键约束失败；
- 更新数据提示"用户不存在"；
- 空指针异常；
- 甚至误操作到其他数据。

### 推荐做法

在拦截器或 Filter 中增加用户状态校验：

```text
1. 解析 JWT，验证签名和过期时间
2. 从 JWT 中获取 userId
3. 根据 userId 查询数据库用户
4. 如果用户不存在、已删除、已禁用，返回 401
5. 如果用户正常，才放行
```

更完善的方案可以结合：

| 方案                  | 适用场景                |
| --------------------- | ----------------------- |
| 拦截器查用户是否存在  | 用户被删、被封禁        |
| Redis 黑名单          | 退出登录、强制下线      |
| token_version 版本号  | 改密码后让旧 Token 失效 |
| Access Token 短有效期 | 降低 Token 泄露风险     |

学习阶段可以先实现：**JWT 验签通过后，拦截器里查一次用户是否存在**。

---

## 问题二：银行卡等敏感信息应该存在哪里？

**不要放进 JWT，应该存在服务端数据库里。**

### 为什么不能放 JWT

JWT 的 Payload 只是 Base64Url 编码，不是加密。任何人拿到 Token 都可以解码看到内容。

所以以下信息都不适合放进 JWT：

- 银行卡号；
- 身份证号；
- 手机号；
- 密码；
- CVV / 支付密码；
- 详细地址等敏感隐私。

### 正确做法

JWT 里只放最小必要信息，例如：

```json
{
  "sub": "10001",
  "role": "user",
  "exp": 1730000000
}
```

前端需要银行卡信息时，通过接口请求：

```http
GET /api/user/bank-cards
Authorization: Bearer <token>
```

后端处理流程：

```text
1. 解析 Token，获取 userId
2. 验证用户是否存在且未被禁用
3. 查询数据库中该用户的银行卡信息
4. 脱敏后返回，例如 **** **** **** 1234
```

### 记忆原则

- **JWT 只放"你是谁"和"你能干什么"。**
- **敏感数据永远存在服务端数据库。**
- **前端需要时通过接口获取，由后端鉴权、查库、脱敏后返回。**

## 问题三：每个接口都校验 JWT 会不会很消耗性能？

**不会。JWT 本地验签本身非常快，每个接口校验一次在绝大多数项目中完全没问题。**

### JWT 验签成本

JWT 验签本质是本地计算：

- Base64 解码；
- JSON 解析；
- 签名校验。

使用常见的 **HS256** 算法时，单次验签通常在 **几十微秒到零点几毫秒** 级别。相比之下，一次数据库查询、远程调用或 Redis 访问通常要慢得多。

真正影响性能的往往不是 JWT 验签，而是：

- 每次请求都查数据库；
- 每次请求都调用远程服务；
- 每次请求都查 Redis 黑名单；
- 拦截器里重复解析 Token；
- 没有复用 JwtParser 等解析对象。

### 放在拦截器里是否合适

合适。拦截器/过滤器正是做认证和授权的常见位置。

更推荐的分层：

| 层级                  | 职责                   | 是否适合验签   |
| --------------------- | ---------------------- | -------------- |
| Filter / 安全过滤器链 | 认证：判断用户是谁     | 适合           |
| Interceptor           | 授权：判断能否访问接口 | 适合           |
| Controller            | 业务逻辑               | 不适合重复验签 |

建议把 JWT 解析放在 Filter 或 Spring Security 过滤器链中，越早拦截越好，避免无效请求进入业务层。

### 学习阶段实现建议

1. 编写 JWT 工具类，**全局复用同一个 JwtParser**；
2. 在 Filter 或 Interceptor 中解析 Token；
3. 验证签名和过期时间；
4. 把 `userId`、`role` 放入请求属性或 ThreadLocal；
5. Controller 中直接获取用户信息，不再重复解析。

### 高并发时的优化方向

只有当项目达到较高并发时，才需要考虑进一步优化：

- 优先使用 HS256；
- 复用 JwtParser，避免每次 new 对象；
- 对已验证 Token 做短时间本地缓存；
- 需要强制下线时再引入 Redis 黑名单；
- 用户状态校验可加缓存或降低频率。

### 结论

**每个接口校验 JWT 不会明显拖慢系统。**
真正要注意的不是"每次验签太慢"，而是"验签之后是否还频繁查数据库、查远程服务、重复解析 Token"。现在按 Filter/Interceptor 每次校验即可，这已经是标准做法。
